# eudkit 0.1.1 release notes

Released 2026-10-28. This is the first editor-MVP release: the shared
`eudkit-lsp` server, a VS Code extension, and a Zed dev extension, built from
the same release tag.

> **Post-`v0.1.1` development note:** hover and signature help for canonical/Map
> Context symbols and the supported eudkit calls were added on the development
> branch *after* this release. The `v0.1.1` assets described here do **not**
> contain them. That work is documented in the
> [user guide](../eudkit-lsp-user-guide.md) and
> [acceptance matrix](../eudkit-lsp-acceptance-matrix.md), and will ship in the
> next release. This document remains the record of what `v0.1.1` actually
> shipped.

User documentation:
[`docs/eudkit-lsp-user-guide.md`](../eudkit-lsp-user-guide.md).

## What is included

- Canonical unit completion for the 228 StarCraft unit names in unit arguments
  such as `KillUnit("...")` in Python, TypeScript, TSX, JavaScript, and JSX.
- Map Context location and switch completion from the nearest `eudkit.toml`
  with a readable `input_map`.
- Canonical fallback without a project: `Anywhere`, `Switch 1`..`Switch 256`,
  and the 228 unit names.
- Unknown Map Symbol warnings and EUD group-player warnings, published with
  source `eudkit`.
- No map-path setting. `eudkit-lsp` discovers `eudkit.toml` from the document
  path.
- `eudkit-lsp --version` and `--stdio` support, with the extension enforcing
  the `0.1.x` compatibility rule.

The release also fixes the release workflow so `--stdio` starts a normal stdio
session and the package versions are derived from and checked against the
release tag.

## Supported platforms

| Platform | Architecture | `eudkit-lsp` asset |
| --- | --- | --- |
| Windows | x86_64 | `eudkit-lsp-windows-x86_64.exe` |
| Linux | x86_64 | `eudkit-lsp-linux-x86_64` |
| macOS | arm64 | `eudkit-lsp-macos-aarch64` |
| macOS | x86_64 | `eudkit-lsp-macos-x86_64` |

Other combinations are unsupported by the published assets. Use a locally
built `eudkit-lsp` through `eudkit.lsp.path` (VS Code), `EUDKIT_LSP_PATH`
(either editor), or `PATH`.

The VS Code VSIX is platform-neutral. Zed uses the source archive
`eudkit-zed-0.1.1.tar.gz`; installing it as a dev extension requires Rust and
the `wasm32-wasip2` target, but the server itself is a native binary and does
not need Rust.

## Separate binaries

The release publishes two independent binaries:

- **`eudkit`** — the build CLI (`build`, `inspect`, `dump-ir`, `watch`,
  `migrate`). This is not used by either editor extension.
- **`eudkit-lsp`** — the language server used by both editor extensions.

Editor assets:

- `eudkit-vscode-0.1.1.vsix` + `.sha256`
- `eudkit-zed-0.1.1.tar.gz` + `.sha256`
- the four `eudkit-lsp-*` assets + `.sha256` companions

Every binary and editor artifact has a published SHA-256 companion. Downloads
without a valid companion are rejected. `BINARY-SIZES.txt` records the size of
each `eudkit` and `eudkit-lsp` build.

## Version compatibility

The editor contract is:

> Editor extension `0.1.x` accepts `eudkit-lsp` `0.1.x`. Patch releases stay
> compatible within the series. A `0.2.x` server requires a matching extension
> update.

- **VS Code** enforces this at runtime by running `eudkit-lsp --version` after
  resolving or downloading the binary. A mismatch is an actionable error, not a
  silent start.
- **Zed** cannot execute arbitrary commands through extension API 0.7. It
  enforces compatibility structurally: the download URL and cache are pinned to
  the extension package version (`0.1.1` → `v0.1.1`) and the checksum is
  mandatory. Do not copy a binary from another release series into the cache.

Do not mix an `0.1.x` extension with an `0.2.x` server. Install the matching
release assets instead.

## Installation

- VS Code: download the VSIX, verify its checksum, and run
  `code --install-extension eudkit-vscode-0.1.1.vsix`. No Rust is required; the
  extension downloads and verifies `eudkit-lsp` on first use.
- Zed: download the source archive, verify its checksum, install it with
  **Install Dev Extension**, and open a supported file. See the
  [user guide](../eudkit-lsp-user-guide.md) for the full walkthrough.

## Known limitations and MVP exclusions

The canonical list is in the [user guide's MVP exclusions](../eudkit-lsp-user-guide.md#mvp-exclusions).
Release-facing highlights:

- Per-map `.d.ts`/`.pyi` generation by the editor or language server, and
  automatic wiring of generated stubs into Pylance/tsserver, are out of scope
  for this editor MVP. The compiler's separate declaration-generation features
  are not part of the editor acceptance.
- Inline compiler diagnostics are out of scope. `eudkit build` errors do not
  appear in the editor Problems panel; run the CLI or CI for compile errors.
- There is no map-path setting or `eudkit.inputMap` setting.
- Custom `UNIx` names are accepted by diagnostics when a map is loaded but are
  not added to `KillUnit` completion.
- At `v0.1.1`, eudkit does not provide API types, hovers, signatures, or type
  checking. Pylance and tsserver remain responsible for host-language types.
  (Hover and signature help are post-`v0.1.1` development work and are not part
  of these assets; see the note at the top.)
- Zed ships as a dev-extension source archive, not a registry package.
- Python, TypeScript, and JavaScript are the reference languages; TSX/JSX are
  registered and share the same server behavior.
- StarCraft runtime validation of display-resource/EWait work is deferred and
  is not part of this release. See
  [`docs/todo/display-resource-ewait.md`](../todo/display-resource-ewait.md).

## Verification

See the [acceptance matrix](../eudkit-lsp-acceptance-matrix.md) for the
per-language, per-editor results, the protocol test suite, and the release
download/checksum evidence. The release VSIX was checksum-verified and installed
in a clean VS Code profile without Rust; the installed bundle then passed the
VS Code behavior matrix, with the server cache cleared so the first run
downloaded the published Linux x64 asset. The Zed extension was verified to
load and start `eudkit-lsp` for Python, TypeScript, and JavaScript; the Zed
completion and diagnostic UI was not automated and remains a manual checklist.
