The MVP exclusions are stated in the guide and release notes:

- no per-map `.d.ts`/`.pyi` generation by the editor or language server;
- no inline compiler diagnostics;
- no map-path or `eudkit.inputMap` setting;
- no custom `UNIx` names in completion;
- no eudkit-provided general API types or type checking. Hover and signature
  help are limited to canonical/Map Context symbols and the supported calls;
  they shipped in `v0.1.2` and are not in `v0.1.1`.

## #54 hover and signature help

Issue [#54](https://github.com/Tb1281/eudplib/issues/54) adds:

- hover for canonical and Map Context unit/location/switch strings, including
  the symbol name, canonical-versus-map status, ID, and Stock Unit Filter ID;
- hover for the 16 supported calls with signature, summary, return type, and
  symbol-accepting parameters;
- signature help in Python, TypeScript, and JavaScript, including comma-based
  active parameters, Python keyword arguments, and qualified
  `eudkit.KillUnit(...)` calls;
- protocol tests for capability advertisement, hover, signature help, and
  no-result behavior.

Deliberate qualified-call rule: a TypeScript/JavaScript member call is analyzed
only when its final member name is a supported eudkit API; the receiver is not
constrained. `eudkit.KillUnit(...)` and the legacy `eud.KillUnit(...)` therefore
complete, hover, and show signatures, while `console.log(...)` and
`eudkit.DisplayText(...)` remain unsupported. The old `eud.KillUnit(...)`
"must not complete" protocol case was removed and replaced with positive
qualified-call coverage plus negative unrelated-member coverage.

State: merged into `feat/lsp-mvp` at `63863e72` (initial merge `769e37e6`) and
shipped in `v0.1.2`. It is not part of `v0.1.1`.

### Review dispositions

Accepted judgement calls from the #54 review (no further refactor planned):

- Keep `CallContext` and `CallSite` separate. They model different token
  sources; sharing one type would force dummy fields into both.
- Keep language selection as `&str`. It matches LSP language IDs and the
  existing server style.
- Keep the small location/switch hover duplication. It is local and clear
  enough that a shared abstraction would not pay for itself.
- Keep canonical resolution in `validation.rs` and import it from `hover.rs`.
  Resolution is genuinely shared with diagnostics; moving it is future work.
- Accept that adding one supported call touches the symbol and documentation
  tables. The layers are intentionally separate and the table-sync tests catch
  drift.
- Treat `docs/todo/display-resource-ewait.md` as a deferred design record, not
  an active spec; the TODO states this explicitly.

## EWait / display-resource work — deferred

Display-resource/EWait work is deferred until the LSP/eudkit documentation is
closed and a 32-bit and/or 64-bit StarCraft client is available for runtime
testing. The decision, options, open questions, and probe plan are in
[`docs/todo/display-resource-ewait.md`](../todo/display-resource-ewait.md).

Summary:

- EWait is a 32-bit real-memory write primitive, not an EUD `SetMemory` write.
- 64-bit Wait/flag/freeze addresses are undocumented, and there is no public
  64-bit offset table.
- No 64-bit client or binary is available here to probe.
- Do not add an `ewait_write` primitive or change `display_at` until the probe
  answers the persistence questions.
- `EWait.py` remains an untracked local reference. Do not commit it.

## Repo gotchas

- The Rust workspace is `src/rust`; there is no root `Cargo.toml`.
- Do not commit changes to the `src/epscript/pybind11` submodule pointer.
- `eud-domain-knowledge/` is intentionally gitignored.
- The `eudkit` CLI remains a separate lean binary from `eudkit-lsp`.
- Zed cannot run `eudkit-lsp --version` through extension API 0.7; compatibility
  is enforced by the pinned tag/cache and mandatory checksum.
- The VS Code extension has no map-path setting; `eudkit.lsp.path` only points
  at the server binary.
